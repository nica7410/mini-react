# 후속 연구 ④: 명시적 memo()를 이용한 행 단위 재사용

2026-11-09. 사용자가 ③(keyed 앞뒤 일치 구간)과 ④ 중 ④를 선택했다. ② 이후 1,000개 진단에서 바뀌지 않은 행을 다시 만들면서 드는 동결·비교·평가 비용이 CPU self의 약 40%였기 때문이다. [근거](followup-trace-alloc.md#다음-연구-후보③④에-대한-근거) · [측정 계획](validation/followup-row-memo/timing-plan.md) · **10,000개는 측정하지 않았다(사용자 지시).**

## 설계

| 요구 | 구현 |
|---|---|
| 명시적 opt-in | `memo(component)`가 새 순수 컴포넌트를 돌려준다. 감싸지 않은 컴포넌트는 지금처럼 매번 실행한다. 일반 자식의 자동 props memo가 아니다. |
| 재사용 조건 | 같은 논리 위치의 이전 **확정** 평가 기록이 같은 컴포넌트 type·key이고(`sameExpressionType`), 모든 own prop(string·symbol 키)이 `Object.is`로 같을 때만 실행을 건너뛰고 이전 기록을 돌려준다. 엔진 재사용 옵션을 끄면 memo도 꺼진다. |
| 오래된 콜백 방지 | 이벤트 handler 함수도 prop으로 비교한다. 다른 함수가 오면 다시 실행해 새 handler를 VNode에 넣는다. |
| State·Hooks | 루트에서만 사용한다. memo 컴포넌트도 `pureComputation` 안에서 실행되는 순수 함수다. |
| 실패한 렌더 | 평가 상태는 commit이 성공한 뒤에만 확정된다. 실패한 시도에서 평가한 행은 다음 시도에서 재사용되지 않는다. |
| 삭제·재삽입·key/type 변경 | 이전 기록이 없거나 type·key가 달라 다시 실행한다. |
| dirty 입력 | 재사용한 행도 Diff의 같은 VNode 경로에서 dirty controlled 입력을 복원한다. |
| 계약 | memo()는 모듈 범위에서 한 번만 호출한다. 건너뛴 memo 컴포넌트의 하위 트리 전체(감싸지 않은 자식 포함)가 함께 재사용되므로, 하위 트리는 `Object.is`로 비교하는 props에만 의존해야 한다. |

**앱 A2.** `TaskAppWithRowMemo`는 rename/toggle/remove 콜백을 `useMemo([setItems])`로 고정하고 `memo(TaskRow)`를 쓴다. 목록 표현은 매 render 다시 만들지만, item 객체와 콜백이 같은 행은 이전 평가를 재사용한다. 한 행을 바꾸면 그 행만 다시 실행한다.

**정확성 테스트**(커밋 `a1b070f`의 `tests/integration/memo-rows.test.ts`; 보류 후 현재 소스에서는 제외됨):
- T-M05: prop·handler·key 변경, 재사용 off, 검증 실패한 렌더 뒤 재시도, NaN·±0·추가/undefined prop·symbol prop, 위치 기반 행, 컴포넌트 root인 memo, 중첩 memo, 삭제 후 재삽입.
- T-A06: A0와 A2에 draft·rename·toggle·delete·add·move를 차례로 적용해 HTML과 입력값이 같은지 확인한다. 행 실행 수는 A0 `[8, 8, 8, 7, 8, 8]`, A2 `[0, 1, 1, 0, 1, 0]`이다. 재사용한 행의 dirty controlled 입력 복원과 최신 State 콜백도 확인한다.
- T-A04/T-A05: A0·A2 모두 대상이다.

별도 코드 리뷰에서 차단 문제는 없었다. 지적 사항(주석, symbol 키, null props, trace 이름, 카운터 분리, 문서화, 경계 테스트)을 반영했다.

## 판정: 보류, 기본 경로는 A0 + `3e9a48c` 유지

**측정 환경이 사전 기준을 만족하지 못했다.** 실행 전에 "같은 E7-A0 build가 1시간 30분 전 `followup-alloc-confirm-v1`과 비교해 조건별 median 변화의 중앙값이 ±10%를 넘으면 추가 측정 없이 결론을 보류한다"고 적었다. 같은 build가 v1에서는 +23.5%(범위 −23.3~+109.6%), v2에서는 **+40.7%**(범위 −28.3~+150.0%) 느렸다. 한 실행 안에서도 세션 간 차이가 컸다(v1 100개 crud S1 67.3 / S2 98.0 / S3 112.0ms). 측정 직후 CPU 부하는 8%였지만 다른 데스크톱 앱이 실행 중이었다.

- **엔진 쌍(E7→E9):** memo를 쓰지 않는 A0에서 엔진 차이는 일치한 컴포넌트마다 WeakSet 조회 한 번이다. 초과 조건은 세션마다 방향이 바뀌어 회귀인지 잡음인지 판정할 수 없다.
- **앱 쌍(A0→A2):** 같은 세션 안의 쌍 비교로 두 실행 모두 큰 감소를 보였지만, 같은 사전 규칙에 따라 채택하지 않았다.
- **조치:** `dcb2310`에서 `src`·`tests`를 `3e9a48c`와 바이트 단위로 같게 되돌렸다. 이 소스는 이미 [최종 검증](validation/task-followup-20261109-v1/result.json)(219/219, Chromium+Firefox 33/33 × 3)을 통과했다. ④ 구현은 커밋 `0855612`(memo·A2), `b201f93`(A2 기본 후보), `a1b070f`(리뷰 반영)에 남아 있고, 측정한 고정 build는 `a1b070f`에서 그대로 다시 만들 수 있다.
- **재측정 조건:** 다른 무거운 앱을 닫은 환경에서 같은 계획으로 다시 측정하고, 먼저 E7-A0 기준선이 `followup-alloc-confirm-v1`과 ±10% 안에 드는지 확인한다. **10,000개는 측정하지 않는다.**

## 문제 조건 5개 보충 측정 (2026-11-09)

v1·v2 원자료와 summary를 대조한 결과, 세션별 허용 증가량을 한 번이라도 넘은 조건은 앱 4개와 엔진 23개였다. 이번에는 고정 빌드로 앱 4개와 엔진 `persistent/crud/10`을 순차 측정했다. 각 비교군은 독립 3세션에서 warm-up 10회, 정식 측정 180회를 수행했다. 같은 세션의 비교쌍에 원래 허용치를 적용했고, 과거 alloc 대비 ±10% 기준은 이번 판정에서 제외했다. [세션별 통계, 해시, 원자료](bench/followup-rowmemo-supplement-20261109-1952/report.md)

- **기능 oracle**은 30개 브라우저 실행에서 모두 통과했다. 측정은 6분 52.6초에 끝났으며 중단은 없었다.
- **앱 A0→A2**에서 `dirty/100`의 초과가 재현됐다. S1·S3의 median은 각각 +0.550 ms(허용 0.500 ms), p95는 +1.635·+3.525 ms(허용 1.000 ms)였다. S2와 `counter/10`, `search/100`, `filter/1000`의 세 세션은 허용치 이내였다. 변동의 원인은 미확인이다.
- **엔진 E7→E9**의 `crud/10`은 workload 전체와 하위 동작 5개 모두 세 세션에서 허용치 이내였다. 기존 초과 조건 중 나머지 엔진 22개는 이번 보충에서 미측정이다.

기존 확인에서 관찰한 A2의 큰 median 개선과 위의 초과 결과를 함께 보존한다. ④의 채택 판단은 보류 상태다.
