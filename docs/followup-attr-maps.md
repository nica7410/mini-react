# 속성 맵 표현 R1 채택 (2026-11-10)

[검증 이름 검사 V1](followup-validate-names.md) 뒤 Node 탐색에서 후속 후보로 고른 속성 맵(`attrs`) 표현을 바꾼 작업이다. 판정 기준은 측정 전에 고정했다. [측정 전 계획](validation/followup-attr-maps/plan.md)

## 결론

- **R1을 채택했다.** 완성된 null prototype과 own 속성 계약을 유지하면서, 해당 Node 탐색에서 fast properties로 관찰된 생성 방식을 적용했다. 완성된 맵의 관찰 가능한 모습(prototype, own 키와 순서, 값, 동결 상태)은 전과 같다.
- 같은 페이지 쌍 비교에서 `diff()`가 조건 A/B/C **−25.7% / −25.0% / −26.9%**(호출당 135~145 µs), 한 행이 바뀐 재렌더링 + `diff()`가 **−20.2%**(215 µs) 감소한 것을 관측했다. 3개 라운드와 두 실행 순서 전부에서 사전 기준(10% 이상, 대조군 참고값 초과)을 넘었다. 이 수치는 고정된 세 iframe 배치에서 얻은 관측이며, 구현과 iframe 위치·realm의 영향이 완전히 분리된 결과는 아니다.
- 100행 전체를 새로 렌더링하는 F는 해당 실험과 사전 판정 기준에서 회귀가 관측되지 않았다(쌍별 중앙값 −4.4%). 이 감소는 대조군의 순서 효과보다 작은 집계가 있어 안정적인 개선이나 다른 조건의 비회귀 보장으로 주장하지 않는다.
- 서로 다른 실험에서 기록한 같은 100행 TaskApp의 `diff()` 호출당 중앙값은 V1 전 약 650 µs, R1 적용 시 약 405 µs였다. 기준 코드가 다른 두 실험의 값을 이어 붙인 것이므로 하나의 직접 전후 비교로 해석하거나 감소율을 합산하지 않는다.

## 1. 무엇이 느렸나

엔진은 속성 맵을 `Object.create(null)`로 만들었다. `constructor`나 `__proto__` 같은 이름이 평범한 속성 데이터로 다뤄지고 `Object.prototype`의 영향을 받지 않게 하기 위해서다. 이번 Node 24/V8 13.6 탐색에서는 이 방식의 속성 맵 728개가 dictionary 방식으로, R1 방식의 728개 맵은 fast properties로 관찰됐고 아래 순회 시간 차이가 있었다. 이 내부 표현과 성능 차이를 모든 V8 버전·객체 형태·브라우저의 보장으로 일반화하지 않는다. Chromium에서는 시간 차이를 측정했으며 내부 표현 자체를 직접 확인한 것은 아니다. `validateTree`는 요소마다 `Object.keys(attrs)`를 부르고, `diff()`는 검증을 두 번 한다.

Node 24에서 잰 탐색 수치(판정 자료 아님, 속성 맵 728개):

| 만드는 방법 | 생성 (ns/개) | `Object.keys` + 값 읽기 (ns/개) | fast 속성 | prototype |
|---|---:|---:|---|---|
| `Object.create(null)` + 대입 (이전) | 397 | 131 | 0/728 | null |
| 빈 동결 prototype의 생성자 + 대입 | 102 | 31 | 728/728 | 빈 동결 객체 |
| 위와 같이 만든 뒤 `setPrototypeOf(null)` (**R1**) | 297 | 29 | 728/728 | null |
| `{}` + `defineProperty` + `setPrototypeOf(null)` | 839 | 30 | 728/728 | null |

## 2. R1이 하는 일

[src/core/attrMap.ts](../src/core/attrMap.ts)의 두 함수를 `resolve.ts`와 `capture.ts`(엔진이 속성 맵을 만드는 두 곳)에서 쓴다.

- `createAttrMap()`: "prototype이 없는 빈 동결 객체" 하나만을 prototype으로 가진 객체를 만든다. 여기에 대입하면 항상 own 데이터 속성이 생긴다. prototype 사슬에 `Object.prototype`이 없으므로 setter나 쓰기 금지 값이 끼어들 수 없다.
- `finishAttrMap()`: 다 채운 뒤 prototype을 null로 바꾼다.

바뀌지 않는 것: 완성된 맵의 prototype(null), own 키·순서·값·서술자, 특수 이름 처리, 검증 정책(E1), Diff·Patch 코드, 오류 메시지. 생성 절차를 바꿨고 해당 Node 탐색에서 내부 표현의 차이를 관찰했다. 두 번째 줄의 방식(prototype을 되돌리지 않음)은 생성이 더 빠르지만 `Object.getPrototypeOf(attrs)`가 달라지므로 택하지 않았다.

## 3. 같은 동작이라는 근거

[테스트](../tests/unit/attr-maps.test.ts)는 기대값을 테스트 안에서 예전 알고리즘으로 따로 계산해 비교한다. 채택 전에는 기본 엔진과 후보를 함께 검사했다(30개), 채택 뒤에는 기본 엔진을 검사한다(검토 뒤 보강해 16개).

- resolver가 만든 맵 10가지: 일반 이름, `__proto__`(own 속성), `Object.prototype` 멤버 이름, 대소문자 충돌, boolean·null·undefined·숫자 값, 빈 맵, 속성 24개, 구두점 이름. prototype·own 키 순서·서술자·동결·`in`·`for-in`·상속 부재를 확인한다.
- `Object.prototype`에 accessor와 쓰기 금지 값을 심어도 읽기·쓰기가 한 번도 일어나지 않는다.
- `__proto__`·`constructor` 속성이 DOM까지 가고 Diff·commit으로 제거된다.
- DOM에서 읽은 맵(`readDOM`)도 같은 조건을 만족한다.
- 변이 4개(prototype을 되돌리지 않음, 평범한 객체로 만듦, resolver가 마무리 생략, DOM reader가 마무리 생략)를 모두 검출했다. [후보 기준](validation/followup-attr-maps/mutations-candidate.json) · [기본 소스 기준](validation/followup-attr-maps/mutations.json)
- 측정 번들의 세 arm에서 트리와 전체 `PatchPlan`의 구조가 같았고, 속성 맵 727개가 모두 null prototype·동결이었다. [사전 검증](bench/attr-map-paired-20261110-d48332e/preflight.json)

독립 검토(작성과 분리한 읽기 전용 검토, `2d92347` 대상)에서 동작이 달라지는 반례는 나오지 않았다. 검토자는 대입이 실패하거나 가로채일 수 없는지, `setPrototypeOf`가 던질 수 없는지(동결은 그 뒤에 일어난다), 중간 예외나 사용자 `toString`이 반쯤 만든 맵에 닿을 수 없는지, 속성 맵을 만드는 곳이 두 곳뿐인지를 코드로 확인했고, 원자료에서 중앙값과 판정을 다시 계산해 요약과 일치함을 확인했다. 검토자는 테스트·빌드·측정을 실행하지 않았다. 지적 사항과 처리:

- 채택 뒤 "기본 resolver와 같은 트리" 테스트가 자기 자신과의 비교가 됐다. → 폼 요소·형제·부모의 맵을 각각 독립 기대값과 비교하도록 바꿨다.
- 값의 문자열 변환이 예외를 던지는 경우의 테스트가 없었다. → 추가했다(렌더링이 중단되고 다음 렌더링은 정상).
- 정수 모양 이름("0", "1")과 동결된 `Object.prototype`은 테스트에 없다. → 그대로 둔다. 정수로 시작하는 이름은 검증이 거절해 완성된 맵으로 나올 수 없고, `Object.prototype` 동결은 되돌릴 수 없어 같은 프로세스의 다른 테스트를 오염시킨다. 두 경우 모두 검토자가 별도 스크립트로 옛 방식과 같은 결과임을 확인했다.
- R1은 모든 라운드에서 셋째 iframe에 고정되어 있어 구현 차이와 iframe 위치·realm·생성 및 초기화 순서의 영향을 완전히 분리하지 못했다. 첫째·둘째 B0 대조의 전체 차이가 0 µs 안팎이라는 관측은 셋째 iframe의 영향을 배제하지 않는다. 따라서 diff의 135~145 µs 감소는 이 고정 배치에서 관측한 차이로 기록하며, 위치에 독립적인 R1의 순수 효과로 확정하지 않는다. 이 한계가 실제 차이의 원인임을 입증한 것도 아니므로 기존 원자료와 사전 기준에 따른 채택 기록은 유지한다.

## 6. 주장 범위와 남은 것

- 확인한 것은 100행 A2 TaskApp의 계산 비용이다: `diff()`, 한 행 재렌더링 + `diff()`, 새 렌더링(DOM commit 제외). Chromium, 한 기기, 한 프로세스의 3라운드, 한 번 실행.
- 확인하지 않은 것: TaskApp 전체 사용자 작업 시간, Patch·paint·GC 비용, 다른 행 수, Firefox 성능(SpiderMonkey에서의 표현 차이 포함), 실제 한글 IME, 원격 CI. 10,000개 측정은 하지 않았다.
- fast 속성 여부는 V8 내부 동작이다. Node 24(V8 13.6)의 탐색에서 직접 확인했으며, Chromium 151에서는 시간 감소를 관측했지만 내부 표현 자체는 확인하지 않았다. 엔진의 내부 표현 정책에 따라 성능 이득은 달라질 수 있으며, 관찰 가능한 맵의 계약과 내부 표현에 관한 가설은 구분한다.
- `capture.ts`(DOM 읽기)는 측정 페이지의 모듈에 포함되지 않아 성능은 재지 않았다. 동작은 테스트로 확인했다.
- 계획 검증 시뮬레이션(`planValidation.ts`)이 만드는 임시 맵은 평범한 객체 그대로이며 이번 범위가 아니다.
- 테스트와 벤치마크 명령의 실행은 실행 전용 서브에이전트(Haiku)가 했고, 코드·문서·판정은 작성자가 했다.

| 검토한 후보 | 코드 근거와 기대 적용 범위 | 이번에 진행하지 않는 이유 |
|---|---|---|
| 원시값에 대한 불필요한 WeakSet 생성 제거 | `vdom.ts`의 `freezeTree`는 WeakSet을 만든 뒤 원시값에서 반환한다. 새 VNode 생성 경로의 작업을 줄일 여지가 있다. | 작은 유지보수 후보다. 미리 생성한 VDOM의 diff에는 적용되지 않으며, A2의 한 행 갱신은 나머지 행을 이미 재사용한다. 시간 이득은 미측정이다. |
| resolver 내부 문자열 attrs의 동결 절차 특화 | `resolve.ts`에서 새로 만든 attrs의 값은 문자열이므로 일반 깊은 동결보다 좁은 처리가 가능할 수 있다. | 새 렌더링에 효과가 집중된다. 외부 VDOM·Proxy·중첩 데이터의 일반 동결과 구분하는 경계 및 회귀 검증 비용을 추가할 근거가 부족하다. |
| Patch 사전 검증의 반복 복사 축소 | `planValidation.ts`는 같은 노드의 여러 명령에서 임시 VNode·맵을 반복 복사할 수 있다. | 현재 입력에서 지배적 비용이라는 근거가 없고 기존 diff 측정 범위 밖이다. 명령별 검증·접근 순서·중간 금지 쓰기를 보존하는 별도 검증이 필요하다. |

실제 앱에서 새 렌더링 또는 같은 노드의 다중 속성 갱신이 구체적인 병목으로 확인되면 그 경로에 한정해 다시 검토할 수 있다. 현재 C1 재측정이나 새 성능 실험을 시작하지 않으며, 10,000개 실행 금지도 유지한다. 이번 변경은 보고서 해석 정정뿐이다. 코드·테스트·사전 계획·원자료·통계·채택 및 보류 기록은 보존했고, 새 테스트·빌드·벤치마크는 실행하지 않았다.
