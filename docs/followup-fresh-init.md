# fresh/equal/100 초기화·생명주기 p95 초과 분석

2026-11-09, `phase1` HEAD `5659427`에서 시작했다. 작업 트리에는 `docs/followup-row-memo.md`의 기존 미커밋 분석과 `docs/bench/engine-supp-20261109-2113-*` 측정 자료(미추적)가 있었으며, 둘 다 수정하지 않았다. 제품 기본 경로(E7+A0)와 채택 정책은 바꾸지 않았고 커밋하지 않았다.

## 결론

- **원인을 코드로 좁히지 못했다. 개선 후보를 구현하지 않았고 최종 비교 묶음도 실행하지 않았다.** 동일 빌드 A/A의 S1에서 기록된 `x → y` 방향은 통과했다. 같은 표본을 역방향 `y → x`로 비교하면 초기화 p95는 +3.715 ms(허용 2.581 ms), 생명주기 p95는 +5.710 ms(허용 3.8915 ms)로 초과한다. 같은 코드에서도 문제 측정 S2의 증가폭(+2.425 ms, +4.300 ms)보다 큰 차이가 관측됐다.
- **초과는 기록으로 남는다.** `task-e7-a0-v1 → dr-cand-e9-a0` S2의 p95 초과는 원래 기준상 초과다. 이번 분석으로 통과 처리하거나 허용치를 바꾸지 않는다. 다만 이 조건의 n=180 p95 판정은 같은 코드끼리도 넘을 수 있어, 한 세션의 초과만으로 코드 회귀라고 보기는 어렵다.
- **④ 전체와 기본 엔진 채택은 완료 처리하지 않는다.**

## 확인된 사실

### 1. 문제 측정의 재계산

n은 모든 셀에서 180이다. 기능 oracle 실패는 0건이고, 세 세션 모두 counts 결과가 같았다.

- **median 변화의 방향이 일정하지 않다.** 초기화는 −0.35 / +0.80 / −0.20 ms, 생명주기는 −0.65 / +1.05 / −0.70 ms였다.
- **세 세션 모두 먼저 실행한 빌드의 초기화 p95가 높았다.** 먼저 실행한 빌드는 26.610 / 26.335 / 26.305 ms, 나중에 실행한 빌드는 24.405 / 23.910 / 24.430 ms였다. 엔진과 무관하게 실행 순서를 따랐다.
- **S2 초기화의 flush별 `flushMs`(E7 → 후보, median / p95)**
  - 첫 마운트: 1.300 / 1.905 → 1.300 / 2.100
  - 데이터 주입: 9.000 / 10.205 → 9.300 / 11.205
  - Effect 이후 갱신: 10.300 / 13.005 → 10.900 / 13.715
  - render와 commit 모두 차이가 있었다. 구간별 p95를 더해 전체 p95를 설명하지 않는다.
  - 데이터 주입의 `flushMs` p95는 10.205 → 11.205 ms(+1.000 ms)다. 초기화 CPU의 정의에 맞춰 표본마다 이 flush의 `flushMs + effectMs`를 계산한 뒤 p95를 구하면 10.300 → 11.205 ms(+0.905 ms)다. 첫 마운트(+0.195 ms)와 Effect 이후 갱신(+0.710 ms)의 p95 차이는 두 집계에서 같다.
  - 데이터 주입 flush의 세부 구간 p95 변화: render +0.300, diff 0.000, commit +0.210 ms.
- **느린 표본은 연속 인덱스에 몰렸다.** 생명주기 상위 9개는 이렇게 분포했다.
  - S2 후보: 9개 중 7개가 #14–21
  - S1 E7: #28–30
  - S3 E7: #19–21
  - 이런 표본에서는 초기화와 같은 표본의 `equal` 갱신이 함께 커졌다. 예: S1 E7 #29는 초기화 51.3 ms, 갱신 27.4 ms였다.
  - 모든 빌드·세션에서 앞쪽 60개의 생명주기 p95가 가장 높았다.
  - 원인(GC, JIT, 다른 프로세스 등)은 직접 측정하지 않았으므로 확정하지 않는다.

### 3. 코드 대조

고정 빌드 소스 세 개를 비교했다. `task-e7-a0-v1` = `3e9a48c`, `task-e9-a0-v1` = `a1b070f`, `dr-cand-e9-a0` = `a1b070f` + `candidate.patch`. 앱은 세 빌드 모두 `9b52323`의 A0다.

- **E9의 memo 지원이 일반 경로에 더한 작업:** `resolve.ts`의 `component-expr` 처리에 `reuse && old && isMemoComponent(expr.type) && sameProps(...)`가 추가됐다.
  - A0에는 memo 컴포넌트가 없으므로 `WeakSet.has`가 false를 돌려준다. 따라서 `sameProps`는 실행되지 않는다.
  - 조회는 같은 위치·key·type의 이전 기록(`old`)이 있을 때만 일어난다. 그 밖의 추가 작업은 `memoReuses` 카운터 하나다.
  - fresh 초기화의 하위 컴포넌트 실행 210회는 counts에서 확인한 실행 수다. 이 기록은 memo 등록 여부 조회 횟수를 따로 집계하지 않는다.
  - 데이터 주입 flush에서는 초기 목록과 주입 데이터가 `task-1`~`task-8` 키를 공유한다. 이 8개 `TaskRow`는 같은 키·타입의 이전 기록과 매칭되며 새 props로 평가할 때 `WeakSet.has` 경로를 탄다. 데이터 변경으로 새 표현을 만드는 `TaskSummary`도 같은 위치·타입의 이전 기록이 있어 조회 대상이다. 이는 고정 소스의 코드 경로 분석이다.
- **복원 패치가 일반 경로에 더한 작업:** commit마다 `isSyncFormOnlyPlan`이 한 번 실행된다. fresh 초기화와 `equal`은 새 snapshot을 만들므로 첫 비교 `plan.target !== mount.view.snapshot`에서 바로 false가 된다. 이후 기존 그래프 검증을 그대로 실행한다. 1회당 O(1)이다.
- **실행 작업량은 같다.** counts realm에서 두 빌드의 초기화 기록이 같았다.
  - 생성 노드 1,047, 삽입 93, 속성 쓰기 1,232, 프로퍼티 쓰기 142, 리스너 716
  - 루트 실행 3, 하위 실행 210, 행 실행 208, commit 3, Effect setup 4 / cleanup 1
  - `equal` 갱신의 기록도 같았다.
- **원인 해석:** S2에서 p95 증가가 가장 큰 데이터 주입 flush는 memo 조회를 포함한다. 이전 기록이 없는 첫 마운트에서도 p95가 +0.195 ms 늘었다. 기존 계측으로는 데이터 주입 구간의 차이에서 memo 조회의 기여를 분리할 수 없다.

## 진단: 동일 빌드 A/A

질문에 맞는 비교로 A/A 하나만 실행했다. E7↔E9 원본 비교와 E9↔E9+패치 비교는 실행하지 않았다.

- 대상: `dr-cand-e9-a0`를 byte 단위로 그대로 복사한 `fi-aa-cand-a0-x` / `fi-aa-cand-a0-y`. JS `32bcd9c6…`, CSS, HTML 해시가 같은 것을 확인했다([aa-builds.json](bench/fresh-init-aa/aa-builds.json)).

n은 모든 셀에서 180이다. 기능 oracle 실패는 0건이고, counts는 세 세션 모두 같았다. 셀 형식은 median / IQR / p95이며, 변화는 y − x다.

- **같은 코드에서도 허용선을 넘을 크기의 p95 차이가 나왔다.** S1의 `x → y`는 통과했다. 같은 표본을 `y → x`로 읽으면 y의 p95를 기준으로 허용치를 다시 계산해야 한다. 초기화는 +3.715 ms > 2.581 ms, 생명주기는 +5.710 ms > 3.8915 ms로 둘 다 초과한다. 이 역방향 계산은 별도의 측정 결과가 아니다.
- **S1의 느린 표본도 연속 구간에 몰렸다.** x의 #39–44에서 생명주기 50–82 ms가 나왔고, 초기화와 갱신이 함께 컸다. 문제 측정 S2의 #14–21과 같은 모양이다.
- **실행 순서 가설은 A/A에서 1/3 세션만 맞았다.** 먼저 실행한 빌드의 p95가 높았던 것은 S1뿐이고, S2·S3은 반대였다. 순서 효과는 확정하지 않는다.
- median 차이의 절댓값을 비교하면, 문제 측정 S2의 초기화 +0.800 ms는 A/A에서 관측한 최대 차이 0.550 ms보다 컸다. 생명주기 +1.050 ms는 A/A에서 관측한 최대 차이 1.100 ms 이내였다. 이 최대값은 이번 A/A에서 관측한 값이다.

## 원인 가설 정리

| 가설 | 지지 근거 | 반대 근거 | 판정 |
|---|---|---|---|
| E9 memo 조회 비용 | 기존 행과 이전 기록이 매칭되는 데이터 주입에서 `WeakSet.has`가 실행된다 | 조회가 없는 첫 마운트에서도 p95가 증가했다. memo 조회 비용을 직접 계측하지 않았고 초기화 median의 변화 방향은 세션마다 달랐다 | 원인 미확인 |
| 복원 패치 분기 비용 | 모든 commit에서 실행된다 | commit당 O(1)이고 첫 비교에서 바로 false가 된다 | 근거 없음 |
| 번들 차이에 따른 JIT·메모리 배치 차이 | 반증하지 못했다 | 직접 측정이 없다 | 미확인 |
| 세션 안 실행 순서 | 이번 3/3, 과거 초과 4건 중 3건 | A/A에서 1/3, v1 S3·v1 S1 반례 | 경향만 있음, 미확정 |
| 프로세스 안의 일시적 지연 구간 | 모든 빌드에서 연속 인덱스 묶음이 보이고, 같은 코드 A/A에서도 같은 크기로 나타났다 | 원인을 직접 측정하지 않았다 | 현상은 확인, 원인은 미확인 |

## 개선 후보

**구현하지 않았다.** 코드 원인을 지목할 측정 근거가 없었다. 동일 코드 A/A에서 문제 크기 이상의 p95 차이가 재현됐다. 근거 없이 memo 조회를 옮기거나 지우면 효과를 이 측정 방식으로 구분할 수 없고, 계약을 바꿀 위험만 생긴다. 그래서 후보 patch, 해시, 정확성 테스트, 최종 비교 묶음(E9+패치 → 후보, E7 → 후보)은 없다.

## 측정 시간과 미검증 범위

- 공통 측정 예산 15분은 21:48:32에 시작했다(`budget.json`). 실제 측정은 A/A 한 번, 99.0초다. 재시도와 표본 제외는 없었다. 측정 중 빌드·테스트·프로파일링은 겹쳐 실행하지 않았다.
- 미검증 범위:
  - 느린 연속 구간의 원인(GC·JIT·OS 스케줄링·다른 앱). 프로파일링을 하지 않았다.
  - E7↔E9 원본, E9↔E9+패치 직접 비교
  - 엔진 보충 대상 중 이번 분석 범위 밖의 나머지 조건
  - fresh/equal의 10·1,000개
  - Firefox
- 실행 순서와 앞쪽 표본의 영향을 줄이려면 측정 설계 변경(예: 세션 앞 공통 warm-up 프로세스, fresh warm-up 확대)을 검토할 수 있다. 다만 기존 기준과 결과의 비교 가능성이 바뀌므로 이번 범위에서는 하지 않았다.

## 엔진 직접 비교의 이전 보충·1회차·2회차 대조

위 미검증 범위는 A/A 진단 종료 시점의 기록이다. 이후 별도 실행에서 A0 고정 `fresh/equal/100` 한 조건을 대상으로 아래 세 비교를 1회차와 2회차에 각각 수행했다. 두 회차의 고정 빌드·측정 설정은 일치했고, 각 비교의 두 빌드는 새 브라우저 3세션에서 세션당 정식 180회씩 완료했다. 원자료로 재계산한 성능 판정은 각 회차의 `decision.json`과 일치했고, 기능 oracle은 두 회차 모두 통과했다. ### 2회차에서 달라진 지표

| 비교 | 세션 | 초과 지표 | 기준 → 후보 (ms) | 증가량 / 허용치 (ms) |
|---|---|---|---:|---:|
| E7 → 원본 E9 | S1 | 생명주기 median | 32.200 → 33.900 | +1.700 / 1.610 |
| E7 → 원본 E9 | S2 | 초기화 p95 | 41.875 → 53.305 | +11.430 / 4.1875 |
| E7 → 원본 E9 | S2 | 갱신 p95 | 22.640 → 27.380 | +4.740 / 2.264 |
| E7 → 원본 E9 | S2 | 생명주기 median | 33.600 → 35.500 | +1.900 / 1.680 |
| E7 → 원본 E9 | S2 | 생명주기 p95 | 68.485 → 80.705 | +12.220 / 6.8485 |
| E7 → E9+패치 | S3 | 갱신 p95 | 17.220 → 21.315 | +4.095 / 2.000 |

최종 후보 직접 비교의 이전 S2 초기화·생명주기 p95 초과는 1·2회차 모두에서 관찰되지 않았다. 반면 S3의 갱신 p95는 1회차 14.500 → 14.200 ms(−0.300 ms)에서 2회차 17.220 → 21.315 ms(+4.095 ms)로 바뀌었다. 2회차에는 양쪽 p95가 모두 높아졌고 후보 쪽 증가가 더 컸다. 구간별로는 render와 diff의 p95 증가가 commit보다 컸다. 구간별 분위수는 각각 계산했다. [1회차 S3 원자료](bench/fresh-init-three-3/session-3.jsonl.gz) · [2회차 S3 원자료](bench/fresh-init-three-r2-3/session-3.jsonl.gz)

패치 없는 E9에서도 2회차에 초과가 관찰됐다. E7 → 원본 E9의 S2에서는 두 빌드 모두 앞쪽 표본에 긴 지연이 나타났고 E9에서 더 오래 이어졌다. 패치 추가 비교는 두 회차 모두 허용치 이내였다. 2회차 초과는 후보가 먼저 실행된 세션과 나중에 실행된 세션 양쪽에서 관찰됐다. 이 결과로 memo 조회, 입력 복원 패치, 실행 순서의 영향을 분리해 원인을 확정할 수는 없다. [E7 → 원본 E9의 2회차 S2 원자료](bench/fresh-init-three-r2-1/session-2.jsonl.gz)

**최종 후보의 이 조건 판정은 결과 혼재다.** 이전 보충은 초기화·생명주기 초과, 1회차는 전 지표 허용치 이내, 2회차는 갱신 초과로 각각 보존한다. ④ 기본 채택은 보류이며, 다른 엔진 조건의 판정은 각 조건의 기존 기록을 따른다.
