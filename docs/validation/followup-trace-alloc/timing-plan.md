# 후속 ② 탐색 측정 계획 (실행 전 기록, 2026-11-09)

- **질문:** resolve/validate의 임시 할당 감소(`f86f25b`)가 최종 소스(`9b52323`) 대비 실제 TaskApp 갱신 시간을 줄이는가?
- **비교군 2개:** `task-e5-a0-v1` = engine `9b52323` + app `9b52323`(기본 A0), `task-e6-a0-v1` = engine `f86f25b` + 같은 app. 과거 E1 측정값으로 대체하지 않는다.
- **조건:** persistent, workloads `crud`(추가·이름 수정·완료 상태 변경·삭제 하위 action 포함), `search`(새 목록 트리 생성), `counter`(무관한 갱신의 전체 검증 회귀 확인). 크기 100 중심, 10·1,000 경계. **10,000개 제외**(사용자 지시).
- **반복:** 기존 runner 고정값(warm-up 10, n=60), **1세션 탐색**. 소수 표본이므로 p95 개선을 확정하지 않고, median 변화만 방향 확인용으로 읽는다.
- **예상 시간:** 18개 브라우저 프로세스, 약 10분. **상한 `--max-minutes=30`.**
- **중단 기준:** oracle(State·DOM·입력·순서·identity) 실패, 상한 도달, 또는 실행 오류 시 원자료를 보존하고 종료. 자동 후속 측정·재시도 없음.
- **확대 기준:** 세 크기 중 100·1,000에서 median이 일관되게 줄고 회귀가 없을 때만, 독립 3세션 비교를 별도 계획으로 제안한다. 이 탐색 결과를 채택 PASS로 쓰지 않는다.
- **할당:** 같은 두 build에 대해 `diagnose-task --modes=cpu --sizes=1000`(counter/sort/crud, CPU·allocation sampling)을 timing 종료 뒤 별도로 실행해 추정 할당량을 비교한다. 진단 수치는 timing과 합치지 않는다.
- **①(추적·Inspector)은 이 측정 범위 밖이다.** TaskApp timing 하네스는 trace sink 없이 실행되므로 ①의 효과는 jsdom의 Inspector 노드 수·재렌더 시간으로 따로 기록한다.

## 확대 확인 계획 (탐색 결과 확인 뒤, 실행 전 기록)

- **탐색 결과:** `followup-alloc-explore-v1` 1세션에서 E5→E6 median이 30개 비교 모두 감소(−10.5~−31.0%). p95는 100개 search에서 +17.6%(+2.5ms) 한 건 증가. 진단(1,000개 cpu)에서 validateTree inclusive 약 47~49% 감소, 추정 할당 21~23% 감소.
- **리뷰 수정:** 리뷰에서 sparse 자식 배열 hole 처리 차이가 발견돼 `3e9a48c`에서 고쳤다. 확인 측정의 후보는 이 수정이 들어간 `task-e7-a0-v1`(engine `3e9a48c`)이고 기준은 같은 `task-e5-a0-v1`이다.
- **조건:** 독립 3세션, 9개 workload persistent + fresh equal, 크기 10/100/1,000(10,000 제외), 기존 n=60/fresh n=30.
- **예상 시간:** 세션당 약 13분, 합계 약 40분. **상한 `--max-minutes=60`.**
- **판정:** 기준선(E1 비교와 같은 엔진 허용 범위: median `max(5%, 1ms)`, p95 `max(10%, 2ms)`)을 넘는 악화 조건이 있으면 채택하지 않고 보고한다. 이 측정은 엔진 비교이며 앱(A0/A1) 효과와 섞지 않는다.
- **중단:** oracle 실패·상한 도달·실행 오류 시 원자료를 보존하고 종료. 자동 후속 없음.

## 보충 계획 (확대 확인 결과 뒤, 실행 전 기록)

- **확대 확인 결과:** `followup-alloc-confirm-v1` 3세션 75조건 모두 oracle 통과. 73조건은 세 세션 모두 median 감소. 허용 범위 초과는 1건: 10개 crud workload p95 S1 +25.8%(+4.0ms, 허용 2ms). 10개 search median S3 +1.0ms(+50%)는 허용 1ms 경계와 같아 초과로 세지 않았지만 함께 보충한다.
- **보충:** 사전 비교 계획과 같은 방식의 새 3세션 n=180(`--supplement`). 같은 두 build, persistent, 크기 10, workloads crud·search. 원래 표본과 합치지 않는다.
- **예상 시간:** 약 3분. **상한 `--max-minutes=20`.**
- **판정:** 보충의 새 세션에서도 허용 범위 초과가 재현되면 ②를 기본 경로에서 되돌리고 보고한다. 재현되지 않으면 채택하고 10개 조건의 단일 세션 p95 초과는 결과와 함께 공개한다.
