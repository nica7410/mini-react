# 같은 페이지에서 B0·C1 전체 Diff 비교

**판정은 보류.** 한 행 수정(A)과 인접 행 교환(B)의 쌍별 중앙값은 모두 C1이 빨랐다. 사전 기준을 넘긴 라운드는 A에서 0/3, B에서 1/3이다. A/A의 순서별 차이와 B의 라운드별 편차까지 고려하면 planner를 도입할 근거가 부족하다. 역순(C)의 반복 악화나 정확성 위반은 관측되지 않았다. 기본 planner는 B0로 유지한다. [사전 계획](validation/keyed-paired-diff/plan.md)

## 비교 대상과 검증

`8ae389e`의 전체 `diff()` 두 버전을 같은 Vite production 번들에 넣었다. C1은 `reconcile.ts`에서 planner 함수의 import 바인딩 하나만 바꾼 버전이다. `keyedEligibility`와 전체 VDOM 검증 등 나머지 코드를 공유한다. `8ae389e`의 SYNC_FORM 검증 보완과 A2/E9/입력 복원 정책은 유지했다. 원본과 생성 소스의 역변환 검사 및 모듈 의존성 검사를 통과했고, build manifest에 원본·후보·하네스·설정·번들 SHA-256을 기록했다. [빌드 및 소스 해시](bench/keyed-paired-diff-20261110-7783ae5/build.json)

실제 A2 TaskApp의 전체 VDOM을 미리 평가했다. 한 행 이름 변경(A)은 99개, 중앙 50·51번째 행 교환(B)과 역순(C)은 각각 100개 행 VNode를 재사용했다. 행의 memo 컴포넌트 identity, 자식 구조와 controlled 입력을 그대로 사용했다. 앱 Hook 평가 후 Effect를 실행하지 않았고, DOM을 만들지 않고 실제 baseline VDOM으로 `MountView`의 ref/자식 구조를 구성했다. 실제 렌더링에서 새로 생긴 상위 이벤트 handler 참조는 남겼다. 각 조건에서 양쪽 함수에 같은 base와 target 객체를 주고, 고정 planId와 LIS, 기본 VNode 재사용 정책으로 전체 `diff()`를 실행했다.

Keyed 단위 차등·통합 테스트 72/72와 typecheck를 통과했다. 별도 Chromium audit 번들에서 각 함수가 자기 planner만 호출했고, 조건마다 해당 planner에 100개 행 목록 호출이 정확히 한 번 있었다. timing 번들은 planner 계측 없이 빌드했다. 두 번들에서 전체 계획을 비교하고 함수 참조, 원본 입력과 재사용 VNode·ViewNode의 동일성, 이동 대상과 배치 순서를 확인했다. A/B/C의 이동은 각각 0/1/99개, `usedLIS`는 false/true/true, 방문 수는 156/147/147, 재사용 하위 트리 수는 99/100/100으로 일치했다. [Chromium 사전 검증](bench/keyed-paired-diff-20261110-7783ae5/preflight.json)

## 실행 순서와 A/A

라운드를 합쳐 실행 순서별로 나눈 쌍별 차이다. 음수는 상대 이름이 더 빨랐음을 뜻한다. `감소 / 동일 / 증가`는 해당 순서에서의 표본 수다.

| 조건 | 먼저 실행 | 쌍별 중앙값 (µs/회) | 쌍별 Q1 ~ Q3 (µs/회) | 감소 / 동일 / 증가 |
|---|---|---:|---:|---:|
| A | B0 | −20.0 | −50.0 ~ −1.3 | 67 / 1 / 22 |
| A | C1 | −5.0 | −28.8 ~ +28.8 | 53 / 2 / 35 |
| B | B0 | −40.0 | −112.5 ~ +10.0 | 63 / 0 / 27 |
| B | C1 | −7.5 | −43.8 ~ +45.0 | 53 / 1 / 36 |
| C | B0 | −10.0 | −45.0 ~ +20.0 | 51 / 2 / 37 |
| C | C1 | 0.0 | −25.0 ~ +38.8 | 43 / 3 / 44 |
| A/A | B0 | −20.0 | −40.0 ~ +25.0 | 30 / 0 / 15 |
| A/A | B0-repeat | +5.0 | −15.0 ~ +30.0 | 19 / 3 / 23 |

- **A.** 두 순서에서 모두 음수이지만, B0 먼저의 −20.0 µs/회는 같은 함수끼리 비교한 A/A에서도 나타났다. C1 먼저는 −5.0 µs/회이고 사분위 범위가 양쪽 부호에 걸친다. 라운드 중앙값은 전부 사전 참고값 약 20.0 µs/회보다 작았다.
- **B.** 두 순서 전체에서 감소 표본이 과반이지만, B0 먼저와 C1 먼저의 중앙값 차이는 32.5 µs/회다. 1라운드는 B0 먼저 −35.0, C1 먼저 +22.5 µs/회로 방향이 바뀌었다. 3라운드는 두 순서에서 각각 −50.0, −30.0 µs/회로 빨랐다. 전체 중앙값의 크기 20.0 µs/회는 반올림 전 참고값을 부동소수점 자릿수에서만 웃돌았고, 라운드 기준은 3라운드만 충족했다. batch p95는 1·2라운드에서 각각 0.820 ms와 0.350 ms 늘고 3라운드에서 1.125 ms 줄었다.
- **C.** 1·3라운드의 C1 batch 중앙값 자체는 각각 0.150 ms와 0.350 ms 컸다. 인접 쌍에서 구한 중앙값은 −5.0, −7.5, 0.0 µs/회로 반복 악화 기준에 해당하지 않았다. 3라운드 C1 먼저는 +7.5 µs/회였다.
- **A/A.** 같은 B0에서도 라운드 중앙값은 −20.0~+10.0 µs/회였고 순서별 전체 중앙값의 부호가 달랐다. 사전 방식으로 계산한 참고값은 약 20.0 µs/회로 세 조건의 B0 중앙값 1%보다 컸다. 이 수치는 같은 환경에서 얻은 기술통계다. A/A는 조건 A에서만 라운드 마지막에 실행했으므로 B/C나 다른 실행 위치의 변동을 직접 추정하지 못한다.

## 채택 근거와 적용 범위

C1은 앞뒤 일치 구간에서 Map 작업과 임시 자료구조를 줄인다. 이점은 기존 planner 작업량 분석에서 확인됐다. C1은 구간 분기와 지연 getter를 추가하므로 계약을 이해하고 유지하는 데 드는 비용도 있다. 이번 전체 Diff에서는 그 비용을 정당화할 만큼 큰 개선이 A와 B 양쪽에서 반복되지 않았다. 정확성 문제나 이득보다 큰 반복 악화도 관측되지 않아 사전 규칙에 따라 **보류**로 끝냈다. [기존 작업량과 유지 비용 기록](followup-keyed-boundaries.md)

이번 실행에서 확인한 것은 같은 브라우저 페이지에서 같은 A2 TaskApp VDOM에 대한 전체 `diff()` 비용 차이다. 세 라운드는 한 프로세스의 새로고침이며, GC·JIT·실행 순서·외부 부하의 영향은 남는다. TaskApp 전체 사용자 작업 시간의 향상, 과거 `crud/100` 전체 시간 회귀 해소, Patch·paint·GC 비용 감소, 실제 React 대비 우위는 이 실험에서 입증되지 않았다.

## 후속 (2026-11-10)
